# GPT Researcher 复刻：能力收益与内部模块设计（草案）

状态：核心设计参数已确认，等待用户最终审阅，尚未进入实现。

## 1. 项目定位

本项目不是调用一次大模型的聊天机器人，也不是把原仓库克隆下来运行。目标是参照 GPT Researcher 的公开架构，从空目录自行实现一个双阶段深度研究 Agent：

```text
研究主题
→ 制定研究计划
→ 多次联网搜索
→ 提取和整理证据
→ 反思信息缺口
→ 补充搜索
→ 生成带引用的研究报告
```

计划周期为两周，每天约 6～7 小时。第一阶段不追求与上游全部功能一比一对齐，重点是完整复刻主要研究闭环，并能够解释、测试和演示。

## 2. 它主要锻炼什么能力

### 2.1 Agent 底层工作循环

项目最核心的学习目标是理解 Agent 不等于聊天界面。Agent 是由程序控制的多步骤任务循环：

```text
目标 Goal
→ 计划 Plan
→ 行动 Action
→ 工具结果 Observation
→ 更新上下文 State
→ 判断是否继续
→ 最终结果
```

在本项目中：

- Goal：用户提出的研究主题。
- Plan：模型生成的研究子问题。
- Action：调用 Tavily 搜索或读取网页资料。
- Observation：搜索结果、网页内容和证据片段。
- State：当前问题、已访问来源、已有证据、失败记录和调用预算。
- Continue：反思当前资料是否存在缺口，决定是否补充搜索。
- Final：生成带引用的研究报告。

完成后，学习者应当能够不用框架术语，画出并解释一次 Agent 从接收目标到结束的完整执行过程。

### 2.2 LLM API 与结构化输出

将练习：

- 通过 OpenAI-compatible API 调用模型。
- 区分请求参数、响应对象和最终文本。
- 让模型返回固定 JSON 结构，而不是随意文本。
- 用 Pydantic 校验研究计划、证据和报告元数据。
- 处理 JSON 缺字段、类型错误和模型拒绝等情况。
- 统计请求次数、输入 Token 和输出 Token。

对应工程价值：让大模型输出能够被程序可靠消费，而不只是“看起来回答得不错”。

### 2.3 Tool Calling 与外部系统集成

Tavily 在项目中是一个搜索工具。系统需要完成：

```text
Python参数
→ HTTP请求
→ Tavily JSON响应
→ SearchResult对象
→ Agent继续处理
```

将练习：

- HTTP、REST、JSON和鉴权头。
- 第三方 API 封装。
- 超时、重试、限流和空结果。
- 用统一接口替换真实服务与测试替身。
- 避免业务逻辑与某个服务商写死绑定。

这类“把模型接入外部工具和企业系统”的能力与 Agent工程及 FDE工作直接相关。

### 2.4 状态管理与工作流编排

系统不是一次函数调用，需要记录：

- 当前任务 ID。
- 正在处理哪个研究问题。
- 已经搜索多少次。
- 哪些 URL 已访问。
- 哪些来源失败。
- 当前证据集合。
- 是否进入反思阶段。
- 是否达到次数或 Token 上限。

学习目标是理解“状态由 Python 程序掌控，LLM 只提出建议或生成内容”。这为以后学习 LangGraph、Pydantic AI、OpenAI Agents SDK 等框架打基础。

### 2.5 数据建模与引用可追溯性

项目至少需要定义：

- `ResearchTask`
- `ResearchPlan`
- `ResearchQuestion`
- `SearchResult`
- `Evidence`
- `ResearchState`
- `ResearchReport`

每条重要报告内容需要能够追溯到来源 URL。这里锻炼的不是数据库算法，而是把模糊文本转换成边界清楚的数据对象。

### 2.6 错误处理和可靠性

需要面对真实失败：

- Tavily 超时或额度用完。
- 搜索没有结果。
- 网页无法访问。
- 多个结果指向同一来源。
- 模型没有返回合法 JSON。
- 部分子问题失败，但整个任务仍需生成有限结论。
- 达到最大搜索次数后必须停止。

这部分是作品区别于普通 AI Demo 的关键。

### 2.7 自动化测试与 Agent 效果测试

工程测试：

- 使用 `FakeLLM` 固定模型返回。
- 使用 `FakeSearch` 固定搜索结果。
- 测试去重、状态变化、引用编号、失败降级和次数上限。
- 少量真实 API 集成测试与大批量离线测试分离。

效果测试：

- 固定若干研究题目。
- 检查子问题是否覆盖主题。
- 检查来源是否与主题相关。
- 检查重要结论是否有引用。
- 对比修改前后的结果，不凭单次主观感受判断提升。

### 2.8 基础后端与交付能力

在核心闭环稳定后，项目会通过 FastAPI 暴露任务接口，并用 Streamlit 提供演示页面。将练习：

- 接收请求并返回结构化 JSON。
- 区分接口层、业务层和外部服务层。
- 保存与读取研究任务。
- 输出日志和错误状态。
- 用 Docker 提供可重复启动方式。
- 编写 README、架构说明和运行指南。

## 4. 内部模块总览

```text
Streamlit UI / FastAPI
          ↓
   ResearchService
          ↓
   ResearchOrchestrator
     ├── Planner
     ├── SearchProvider ── TavilySearch / FakeSearch
     ├── ContentExtractor
     ├── EvidenceManager
     ├── Reflector
     ├── ReportWriter
     └── UsageTracker
          ↓
   ResearchRepository
          ↓
        SQLite
```

### 4.1 UI与API层

输入：研究主题和少量运行参数。

处理：创建研究任务、显示阶段状态、获取最终结果。

输出：研究计划、进度、来源、错误提示和 Markdown报告。

边界：不负责编写 Prompt、调用 Tavily 或生成报告。

### 4.2 ResearchService

输入：用户请求。

处理：校验主题、创建任务、调用研究编排器、协调保存结果。

输出：任务 ID、任务状态或最终报告。

边界：它是应用入口，不包含具体搜索算法。

### 4.3 ResearchOrchestrator

输入：合法的研究任务。

处理：决定模块调用顺序，维护研究状态，执行第一轮研究、反思和第二轮研究，并检查终止条件。

输出：完整的 `ResearchState`。

边界：它负责流程，不负责搜索细节和报告措辞。

### 4.4 Planner

输入：研究主题。

处理：调用 LLM生成研究目标、范围和若干子问题，并通过 Pydantic校验。

输出：`ResearchPlan`。

失败：重试一次；仍不合法时返回明确失败，不偷偷使用无法验证的自由文本。

### 4.5 SearchProvider

输入：一个搜索问题和结果数量上限。

处理：调用搜索服务并把厂商 JSON转换为统一数据结构。

输出：`list[SearchResult]`。

实现：

- `TavilySearch`：真实联网运行。
- `FakeSearch`：自动化测试。

边界：其他模块不知道 Tavily原始字段。

### 4.6 ContentExtractor

输入：候选搜索结果或 URL。

处理：提取正文、清理明显无关内容、保留标题和来源信息。

输出：可供分析的来源文档。

第一版优先使用 Tavily返回的内容和提取能力，不自行支持所有动态网页。

### 4.7 EvidenceManager

输入：来源文档、研究问题和模型提取结果。

处理：建立证据记录、规范 URL、去除重复来源、分配引用编号。

输出：`list[Evidence]`。

边界：引用编号由确定性代码管理，不能让模型随意编造。

### 4.8 Reflector

输入：研究计划和第一轮证据。

处理：判断哪些子问题证据不足、是否存在信息缺口，并生成有限数量的补充搜索问题。

输出：补充问题列表或“无需继续”。

终止规则：最多进行一轮补充搜索，避免无限循环和成本失控。

### 4.9 ReportWriter

输入：研究主题、计划和整理后的证据。

处理：生成结构化 Markdown报告，只能引用 EvidenceManager提供的来源编号。

输出：报告正文及实际使用的引用编号。

失败：发现未知引用编号时判定报告无效并重试或标记失败。

### 4.10 UsageTracker

输入：每次 LLM和搜索调用的用量信息。

处理：累加请求数、Token、搜索 credits 和估算成本，检查预算。

输出：当前用量及是否允许继续。

### 4.11 ResearchRepository

输入：任务、状态、来源、证据和报告。

处理：写入和查询 SQLite。

输出：历史任务及其完整结果。

边界：编排器不直接编写 SQL。

## 5. 一次任务的数据流

```text
用户提交 topic: str
  ↓
ResearchService 创建 ResearchTask
  ↓
Planner 返回 ResearchPlan
  ↓
Orchestrator 逐个处理 ResearchQuestion
  ↓
SearchProvider 返回 list[SearchResult]
  ↓
ContentExtractor 返回来源文档
  ↓
EvidenceManager 返回 list[Evidence]
  ↓
Reflector 返回补充问题
  ↓
再次搜索和补充 Evidence
  ↓
ReportWriter 返回 ResearchReport
  ↓
Repository 保存任务与报告
  ↓
UI/API 返回最终结果
```

## 7. 已确认的设计决策

以下决策已于 2026-09-12 确认：

- LLM：DeepSeek API，第一版统一使用成本较低、支持结构化输出的模型，不做多模型路由。
- 搜索：Tavily API；自动化测试使用 `FakeSearch`。
- 首轮研究问题：4个。
- 反思阶段补充问题：最多2个。
- 研究轮次：最多2轮。
- 每个问题最多保留5条候选搜索结果。
- 整个任务最多保留12个有效来源。
- 后端：FastAPI。
- 持久化：SQLite，第一版优先使用 Python内置 `sqlite3`，不引入复杂 ORM。
- 演示界面：Streamlit。
- 报告格式：Markdown和HTML。
- 效果测试：3个来源于公开接单平台的 Agent项目需求固定案例。

### 7.1 固定效果测试题目

1. 企业文档问答 Agent：覆盖 PDF解析、RAG、向量检索、引用、权限和隐私。
2. 电商客服 Agent：覆盖商品咨询、订单查询、退款规则、多轮对话和人工转接。
3. 浏览器自动化 Agent：覆盖登录、搜索、表单填写、数据提取、异常恢复和人工确认。

案例必须保存公开来源 URL和采集日期，并移除个人、客户或公司敏感信息。平台内容发生变化后，测试仍使用经过留档的固定输入，保证版本之间可以比较。

### 7.2 效果评价维度

- 需求覆盖率。
- 研究问题的具体性和重复度。
- 来源相关性与可信度。
- 关键结论的引用完整性。
- 风险识别能力。
- 报告可读性。
- 多次运行的稳定性。
- 搜索和 LLM调用成本。

每个固定案例使用同一份评分规则进行人工复核，修改前后必须在相同案例上比较。

## 9. 密钥与运行约束

- DeepSeek在线 API与 Tavily API都需要各自的 API Key。
- Key只能从环境变量或本地 `.env` 读取，不得提交到 Git。
- 创建或修改 `.env` 前需要用户单独明确授权。
- 普通单元测试不得访问真实 API。
- 真实集成测试必须限制问题数、来源数和最大调用预算。
- 达到搜索、轮次或 Token上限后，编排器必须停止继续调用。
